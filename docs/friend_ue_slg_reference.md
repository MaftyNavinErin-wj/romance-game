# Demo 机制参考说明

这份文档是给 Demo 团队看的机制参考，不是 UE 实现方案，也不是最小 MVP 规划。

Demo 设计文档已经明确了方向：有主线目标的开放式战役、持续时间推进、州郡县治理、角色政治关系、地方权力节点、粮道后勤、编制化军队，以及自动战斗和手动战斗共用底层规则。

本 repo 是一个网页三国策略原型。表现层和技术栈不重要，真正有参考价值的是底层机制：经济、人口、粮食红线、豪族属县、武将任命、派系朝议、后勤补给、部队指标、自动战斗、围城、事件触发。这些系统已经在一个可运行原型里互相连接过，可以作为 Demo 机制设计的参照。

下面按游戏板块说明。每一节都按同一套顺序展开：

```text
已有机制 ready 到什么程度
底层逻辑：输入 -> 状态 -> 结算 -> 输出 -> 跨系统影响
为什么和 Demo 设计相关
Repo 里去哪里看
```

## 1. 经济、财政和建设循环

本 repo 已经有一套可运行的城市经济循环。它不是一个总资源面板，而是每座城市独立结算人口生产、粮食库存、建筑、税率、徭役、太守、豪族、腐败，再把金、木、铁、马等非粮资源汇总到势力层。

底层逻辑可以拆成五步：

```text
输入
  - 城市基础产出：base.food / base.gold / base.wood / base.iron / base.horses
  - 城市标签：都市、平原、水乡、港口、山地、产马、产铁、产木等
  - 人口与人口质量：pop / popQuality
  - 建筑等级：农田、市集、水利、港口、马厩、工坊、粮仓、兵营、道路等
  - 势力政策：税率 taxId、徭役 corveeId
  - 治理角色：太守 prefect、官职 buff、朝议法令、科技
  - 地方状态：豪族支持度 gentry、腐败率

状态
  - 城市粮食库存 storage
  - 城市民心 morale
  - 城市人口 pop
  - 城市人口质量 popQuality
  - 建设队列 buildQueue
  - 势力资源 res.gold / wood / iron / horses

结算
  - getCityProd 计算城市当旬产出
  - processCityFood 处理粮食入库、消耗、腐损
  - processMorale 处理民心变化
  - processPop 处理人口和人口质量变化
  - processBuildQueues 推进建设队列
  - processFacEconomy 汇总势力资源，并扣除腐败损耗

输出
  - 本地粮食库存变化
  - 势力财政和材料变化
  - 民心变化
  - 人口和人口质量变化
  - 建设完成或推进
  - 腐败损失和治理效率变化

跨系统影响
  - 粮食不足会影响民心、人口死亡、驻军恢复、前线调粮压力
  - 税率影响财政，同时影响民心和人口增长
  - 徭役加速建设，同时损害民心和人口质量
  - 太守政治能力影响产出、民心恢复、建设速度
  - 豪族支持影响金产、征兵成本、城防、腐败
```

这套逻辑的重点是“经济不是一张收入表”，而是一个持续运行的压力系统。粮食、人口、税率、徭役、建设、太守、豪族会互相牵制。短期拉高税率或徭役能解决资源问题，但会把压力转移到民心、人口质量、地方支持和未来产出上。

这和 Demo 设计的相关性很强。Demo 文档里提到士农工商、人力、经济、粮草、金属、马匹、税、赋、役、道路、粮仓、兵营，这些内容都需要一个能随时间持续结算的经济底座。这里不需要照搬数值，但可以参考变量如何组织成闭环。

Repo 入口：

- `src/chains/economy.js`
  - `getCityProd`：城市产出计算，人口、地形、建筑、太守、豪族、科技都在这里进入公式。
  - `getCityFoodCost` / `getCityFoodNet` / `getCityFoodTurns`：粮食消耗、净值和可撑旬数。
  - `processCityFood`：每旬粮食入库、消耗和腐损。
  - `processMorale`：粮食、税率、占领、太守、豪族、徭役对民心的影响。
  - `processPop`：人口和人口质量变化。
  - `processFacEconomy`：势力资源汇总和腐败扣除。
  - `processBuildQueues`：建设队列、太守和徭役加速。
  - `setTax` / `setCorvee`：税率和徭役入口。
- `src/data/constants.js`
  - `TAX`：税率档位。
  - `CORVEE`：徭役档位。
  - `BLDS`：建筑定义、成本、耗时、限制。
- `src/data/tags.js`
  - 城市/地形标签如何影响粮、金、木、铁、马、槽位、耐久。
- `src/core/tick.js`
  - 每个时间结算周期里经济、人口、建设等函数的调用顺序。

## 2. 人口、粮食红线和地方恢复

本 repo 的人口不是静态资源。人口会自然增长，也会因为粮食不足、战乱、迁民、豪族隐匿户口而变化；人口质量会影响有效生产人口，也会被徭役、战乱、学堂、科技、太守性格等因素影响。

底层逻辑可以拆成五步：

```text
输入
  - 当前人口 pop
  - 人口质量 popQuality
  - 城市承载上限 getCityCap
  - 粮食净值 getCityFoodNet
  - 粮食库存 storage
  - 民心 morale
  - 税率 taxId
  - 徭役 corveeId
  - 城市是否被占领 occupied
  - 附近是否有敌军
  - 学堂、科技、太守性格等恢复因素

状态
  - pop：账面人口
  - popQuality：人口质量
  - storage：粮食库存
  - morale：民心
  - counties[].loyalty：属县豪族忠诚

结算
  - 人口按基础增长率自然增长
  - 增长率受人口质量影响
  - 粮食净值为负且库存为零时，按缺口比例触发饥荒死亡
  - 税率给人口增长带来正负修正
  - 战乱会造成人口流失，并阻止人口质量恢复
  - 徭役在有建设时损害人口质量
  - 学堂、科技、民心、太守性格推动人口质量恢复

输出
  - 人口增加或死亡
  - 人口质量恢复或下降
  - 城市产出能力变化
  - 粮食消耗压力变化
  - 兵源、建设容量、驻军恢复潜力变化

跨系统影响
  - 人口越多，粮食消耗越大，但生产和税赋潜力也越高
  - 人口质量越高，有效生产人口越高
  - 粮食危机先压民心，再造成死亡，再可能引发事件/叛乱
  - 豪族忠诚过低会造成隐匿户口，人口从中央账面消失
  - 迁民可以救前线人口，但会冲击民心、人口质量和属县忠诚
```

Demo 文档里的“粮食红线”可以用两种方式表达。

一种是硬阈值：

```text
当前粮食储量 + 预期粮食产量 < 粮食红线 -> 民乱
```

本 repo 用的是更连续的压力读数：

```text
FoodNet = FoodProduction - FoodCost

如果 FoodNet >= 0:
  粮食压力为 0

如果 FoodNet < 0:
  FoodTurns = FoodStock / -FoodNet
```

这个读数的好处是风险会逐步显现，而不是突然爆炸：

```text
FoodTurns 很高:
  民心稳定，城市可继续恢复

FoodTurns 下降:
  民心开始下降，前线调粮压力上升

FoodTurns 接近 0:
  城市进入饥荒风险，人口死亡即将发生

FoodStock = 0 且 FoodNet < 0:
  按缺口比例造成饥荒死亡
```

这和 Demo 设计相关，因为 Demo 强调县级治理、稳定、人口、粮食红线、民乱升级。人口如果只是“兵源和产粮数字”，系统会比较薄；人口如果被粮食、战乱、徭役、地方豪族共同影响，就会成为治理、军事和政治之间的共同媒介。

Repo 入口：

- `src/chains/economy.js`
  - `processPop`：人口自然增长、饥荒死亡、税率影响、战乱影响、人口质量恢复/损伤。
  - `getCityCap`：人口承载上限。
  - `getCityFoodTurns`：粮食压力核心读数。
  - `executeMigration`：迁民、损耗、民心/质量/豪族冲击。
  - `_aiConsiderMigration`：AI 在威胁下如何迁民。
- `src/chains/gentry.js`
  - `processGentry`：包含县级豪族忠诚过低时的隐匿户口。
- `src/render/tooltips.js`
  - 可以看人口、粮食、属县忠诚如何展示给玩家。

## 3. 地方豪族、属县和权力节点

本 repo 最接近“权力节点”的系统是豪族/属县系统。早期版本只有城市级 `gentry` 数值，后续演化成县级结构：每座城市下辖多个属县，每个属县有类型、家族、人口占比、忠诚度、是否豪强县等字段。

底层逻辑可以拆成五步：

```text
输入
  - 城市所属势力 fac
  - 城市所属州/地域
  - 属县静态数据 COUNTY_DATA
  - 属县类型：seat / clan_base / normal
  - 属县人口占比 popShare
  - 属县绑定家族 clanFamily
  - 太守身份：本县、本城、外来士族、寒门、降将、空缺
  - 本势力任职武将及其籍贯/家族
  - 城市是否被占领、是否被围城
  - 朝议、处决、挖角、迁民等冲击事件

状态
  - counties[].loyalty：每个属县独立忠诚
  - city.gentry：由属县忠诚按人口占比聚合得到
  - counties[].magnate：豪强县标记
  - counties[]._initPop：隐匿户口用的初始人口基准

结算
  - 初始化时按本土/外来政权、家族是否任官，给属县设初始 loyalty
  - 每旬计算共享变化：占领期、势力阶段、技能、科技、自然漂移
  - 每个县再计算太守修正：本县最好，本城次之，外来士族略负，寒门/降将更负，空缺也负
  - 本地武将、本族武将给对应属县或家族据点额外加成
  - 家族级事件直接冲击对应 clan_base 县
  - 最后按 popShare 聚合成 city.gentry

输出
  - 城市级豪族支持度 city.gentry
  - 金产修正
  - 征兵/补员成本修正
  - 城防修正
  - 腐败修正
  - 隐匿户口
  - 被围城时的开城投降风险

跨系统影响
  - 经济链读取豪族支持来修正金产和腐败
  - 军事链读取豪族支持来修正城防和补给通过成本
  - 政治链通过朝议影响对应士族属县
  - 武将链通过处决、归降、任职触发家族态度变化
  - 迁民会同时冲击来源地和目的地属县
```

这套系统的核心不是“地方有一个好感度”，而是把地方权力拆成多个有权重的节点。`popShare` 很关键，因为一个大县豪族不满和一个小县豪族不满，后果不应该一样。`clanFamily` 也很关键，因为它让任命、处决、朝议等政治行为能打到具体地方。

这和 Demo 设计相关，因为 Demo 文档提到地方豪强/士族、资源控制权、暴力控制权、权力节点、县内坞堡群。实现上不一定要把每个村镇都做成完整单位，但可以让关键县、豪族据点、坞堡群成为治理和军事风险的来源。

Repo 入口：

- `src/data/state_county.js`
  - 州、城市到州、属县、家族、豪强县等静态数据。
- `src/chains/gentry.js`
  - `initCityGentry`：开局为每城生成属县结构。
  - `_aggregateGentry`：属县忠诚按人口占比聚合成城级豪族支持。
  - `processGentry`：每旬属县忠诚变化。
  - `applyGentryOnCapture`：城市易主后，属县忠诚按新旧势力和家族关系重置。
  - `applyFamilyLoyaltyShock`：处决、挖角、朝议等对家族属县造成冲击。
  - `getGentryGoldMult` / `getGentryRecruitMult` / `getGentryDefMult`：豪族支持如何进入经济、征兵和城防。
- `src/chains/politics.js`
  - `_applyCourtDecisions`：朝议如何影响派系对应属县。
- `src/chains/general.js`
  - `killGen`：处决/战死如何触发家族忠诚冲击。

## 4. 武将、标签、忠诚、任命和派系政治

本 repo 的武将不是纯战斗单位。武将有不可变基础数据，也有剧本运行时数据；同一名武将会进入战斗、太守、官职、军师、朝议、派系、忠诚、关系、俘虏、劝降等系统。

底层逻辑可以拆成五步：

```text
输入
  - 基础属性：com / war / int / pol / cha
  - 兵种适性 apt
  - 出生地 birthplace
  - 家族 clan
  - 出身/阶层/地域/性格/价值标签 GEN_TAGS
  - 技能 skills
  - 剧本状态：所属势力、身份、官职、忠诚、功绩、部曲、关系、是否在野/待出仕

状态
  - G.generals[fid]：势力拥有的武将
  - G.genLoyalty：当前忠诚
  - G.loyaltyAccum：忠诚累计/平滑状态
  - G.genPost：官职
  - G.genMerit：功绩
  - G.genFactionMod：派系好恶修正
  - 亲密度、仇恨、归降来源、继任状态等关系数据

结算
  - 任官提高忠诚，罢官降低忠诚
  - 官职提供势力级 buff，也改变派系态度和价值倾向
  - 太守任命把武将政治能力接到城市治理，把武将籍贯/出身接到地方豪族
  - 朝议根据派系生成政策提案，采纳/否决后写入法令、派系修正、属县忠诚
  - 战斗、任职、研究等行为给属性经验和功绩
  - 俘虏劝降读取君主魅力、俘虏忠诚、相性、关系、地域、家族等因素

输出
  - 忠诚变化
  - 官职和太守效果
  - 派系影响力变化
  - 朝议法令和政策 buff
  - 地方豪族态度变化
  - 战斗/治理/事件中的角色差异

跨系统影响
  - 经济链读取太守政治和官职 buff
  - 豪族链读取太守籍贯、家族、本地武将任职情况
  - 军事链读取统率、武力、智力、适性、士气和技能
  - 事件链读取忠诚、派系、承诺、封赏、死亡、归降等状态
  - 政治链把角色派系转成朝议和势力内部压力
```

这套系统的关键点是：角色数据必须同时被治理、军事、事件和关系系统读取。否则武将会退化成战斗卡，无法支撑 Demo 文档里“君主通过任命、指派、授权延伸统治”的设计。

Demo 设计里提到地域、出身阶层、政治派系、后天派系、忠诚、利益判断。这里可以参考的不是具体官职表，而是角色怎样成为跨系统连接件：一个任命动作，既改变治理效率，也改变忠诚，也影响地方豪族，也可能改变派系气氛。

Repo 入口：

- `src/data/general_base.js`
  - 武将不可变主表。注释里写了字段边界：哪些是 base，哪些是 scenario-specific。
- `src/data/scenarios/*.js`
  - 剧本运行时武将数据：所属势力、忠诚、功绩、部曲、关系、初始部队等。
- `src/data/tags.js`
  - 武将标签、出身、性格、地域等。
- `src/chains/general.js`
  - `addStatExp`：岗位/战斗带来的属性经验。
  - `getGenFactions`：武将如何归入多个政治派系。
  - `calcSurrenderRate`：劝降如何读取君主魅力、忠诚、相性、关系、地域/家族等。
  - `killGen` / `succeedRuler` / `surrenderGen`：死亡、继承、归降的政治后果。
  - `_applyCeremony`：封赏如何影响忠诚、经验和全军士气。
- `src/chains/politics.js`
  - `appointGenPost` / `dismissGenPost`：任官/罢官对忠诚、派系、价值观的影响。
  - `calcFactionInfluence`：势力内部派系影响力。
  - `calcPostBuffs`：官职如何变成经济、军事、建设、外交等 buff。
  - `_applyCourtDecisions`：朝议采纳/否决的跨系统效果。
- `src/core/tick.js`
  - 太守每旬获得功绩和政治经验，说明任职本身也是成长路径。

## 5. 部队编制、兵牌和战斗指标

本 repo 的大地图军事单位不是“一个武将带一坨兵”。`unit` 由多个 `squad` 组成，每个 `squad` 绑定武将、兵种、兵力、士气等数据。这个结构和 Demo 文档里的兵牌、编制模板、营级单位、列装需求、维持需求很接近。

底层逻辑可以拆成五步：

```text
输入
  - Unit：所属势力、位置、状态、等级、squads
  - Squad：武将、兵种、兵力、最大兵力、士气
  - 武将属性：统率、武力、智力、适性、技能
  - 兵种定义：基础攻击、防御、克制、材料需求
  - 环境：地形、补给、营寨、城防、火攻、伏击等临时状态
  - 势力科技、官职、派系士气等修正

状态
  - unit.status：行军、驻扎、围城、伏击、撤退等
  - squad.troops / maxTroops
  - squad.morale
  - unit food/salary/supply 状态
  - 武将部曲 retainer

结算
  - _squadBase 先把兵力、等级、士气、统率、适性合成基础战力
  - squadATK 在基础战力上叠加兵种攻击、克制、地形、混编、科技、技能
  - squadDEF 在基础战力上叠加兵种防御、地形、营寨/城防、科技、技能
  - calcUnitATK / calcUnitDEF 把 squad 汇总成 unit 指标
  - 战斗、胜率预估、AI 判断都读取这些指标

输出
  - 单个 squad 的攻击/防御贡献
  - 单个 unit 的 ATK/DEF
  - 部队维持消耗
  - 战斗损失、士气变化、补员需求
  - 材料消耗和装备压力

跨系统影响
  - 经济链提供兵种材料、粮食和军饷
  - 后勤链决定是否断粮，断粮影响士气和损耗
  - 武将链提供属性、适性、技能、关系、部曲
  - 战斗链统一使用这些指标进行结算和胜率估算
```

最值得参考的是指标拆分方式。不要把部队压成一个“战斗力”。至少应保留：

- 兵力：决定输出规模和承伤规模。
- 士气：直接乘到实际发挥上，低士气大军会虚胖。
- 兵种：决定基础攻防、地形适应和克制关系。
- 将领：统率影响组织，武力影响个人战斗和冲锋类效果，智力影响计谋/伏击/判断。
- 适性：决定将领带对应兵种的发挥上限。
- 补给：决定能否持续作战。
- 材料/装备：决定能否组建、扩编、补员。

这和 Demo 设计相关，因为 Demo 文档里明确说一个兵牌约等于营级单位，一千到两三千人，总兵力还包括辅兵、征夫、器械操作人员。战斗层如果只有总兵力，自动战斗、手动战斗、战前预估、战后回收会很难统一。

Repo 入口：

- `src/data/constants.js`
  - `TROOP_TYPES`：兵种定义。
  - `TYPE_ATK` / `TYPE_DEF` / 克制、适性、等级等战斗常量。
- `src/chains/military.js`
  - `getUnitTroops`：单位兵力读取。
  - `_squadBase`：兵力、等级、士气、统率、适性等基础战力。
  - `squadATK` / `squadDEF`：攻击/防御值。
  - `calcUnitATK` / `calcUnitDEF`：单位级战斗指标。
  - `getMixedBonusMult`：混编协同。
  - `processUnitFood` / `processUnitSalary`：部队维持。
- `src/chains/economy.js`
  - `calcSlotMatCost` / `canAffordMat` / `deductMat`：兵种材料需求和扣除。
- `src/data/scenarios/*.js`
  - 初始部队和 squad 数据。

## 6. 道路、粮道和后勤覆盖

本 repo 的后勤系统分两层：城市之间调粮，以及地图上的补给覆盖。补给不是手动画一条线，而是从己方城市出发，在 hex 地图上按地形、敌方、领地和地方支持度进行扩散，最后判断部队所在格是否在补给覆盖内。

底层逻辑可以拆成五步：

```text
输入
  - 己方城市位置
  - 城市是否新占、是否恢复补给
  - 地图 hex 和地形
  - 城市/道路/地形节点
  - 敌我领地
  - 可见敌军位置
  - 地方豪族支持度
  - 部队当前位置

状态
  - supplyMap：每个 hex 的剩余补给距离/质量
  - unit._noSupplyTurns：部队断粮累计旬数
  - city.storage：城市粮食库存
  - G.supplyLines / foodAlertCards：调粮和警报状态

结算
  - buildSupplyMap 从己方城市同时出发做 BFS 扩散
  - 每个 hex 按地形扣除补给范围
  - 深入敌境增加额外消耗
  - 可见敌军所在格阻断补给
  - 地方豪族支持影响通过成本
  - isUnitSupplied 判断部队是否在覆盖内
  - processSupplyStatus 累计或清除断粮状态
  - checkResupply 发现缺粮城市并寻找富余城市调粮

输出
  - 某部队是否有补给
  - 断粮持续时间
  - 士气和损耗压力
  - 前线缺粮警报
  - 后方到前线的调粮行为

跨系统影响
  - 经济链决定哪里有粮
  - 地图链决定道路和地形成本
  - 豪族链影响地方通过成本
  - 军事链读取补给状态影响部队表现
  - 事件链可根据断粮、缺粮、围城触发危机
```

这和 Demo 设计高度相关。Demo 文档强调粮道不是抽象补给线，而是基于地图节点、道路条件、粮仓、己方城池、敌方威胁生成的实际运输路径。本 repo 的思路是先做“补给覆盖图”，再由表现层画出路径或风险。这样系统天然支持修路、守粮仓、截断道路、深入敌境、地方不配合等玩法。

Repo 入口：

- `src/chains/military.js`
  - `buildSupplyMap`：补给覆盖图核心，BFS 洪泛扩散。
  - `isUnitSupplied`：判断部队是否在补给范围内。
  - `processSupplyStatus`：每旬处理断粮状态。
  - `SUPPLY_TERRAIN_COST` / `SUPPLY_ENEMY_PENALTY` / `SUPPLY_MAX_RANGE`：补给参数。
- `src/chains/economy.js`
  - `checkResupply`：自动调粮警报和调粮候选。
  - `doTransfer` / `_execTransferFood`：城市间调粮。
- `src/core/map.js`
  - 地图 hex、节点和道路相关基础。
- `src/data/tags.js`
  - 道路、地形、城市标签如何影响资源和战略价值。

## 7. 自动战斗、战斗核心和围城

本 repo 已有自动战斗核心，并且战前估算复用同一套攻击/防御指标。它不是 UE 3D 战场，但具备“自动战斗和手动战斗共用底层”的规则层雏形。

底层逻辑可以拆成五步：

```text
输入
  - attackers / defenders
  - 地形 terrain
  - unit / squad / general / troop type
  - 士气、兵力、等级、适性、技能
  - 补给、伏击、营寨、火攻、城防等临时状态

状态
  - 参战 unit 和 squad 的兵力/士气
  - 临时战斗标记：攻守方、火攻 debuff、伏击结果、单挑结果、连携结果
  - 城市围城状态、城防衰减、守军

结算
  - 计算双方 ATK
  - 计算双方 DEF
  - 套用士气、将领、适性、兵种、地形、混编、技能
  - 触发单挑、连携、伏击、火攻等事件
  - 用随机区间 roll 胜负
  - 按攻防比和结果分配损失
  - 处理士气变化、俘虏、追击、撤退、战死等后果

输出
  - winner / loser
  - 双方损失
  - cpRatio / 胜率相关指标
  - captured / killed / pursued / duel / skillLogs
  - 参战 unit id
  - 城市归属、守军、民心、豪族、声望等战后写回

跨系统影响
  - 军事链修改部队兵力、士气、状态
  - 武将链处理俘虏、战死、单挑、亲密度、仇恨
  - 豪族链处理攻城后安抚/劫掠/屠城
  - 外交链处理声望、信誉、占城后果
  - 事件链可根据战斗结果推进主线或危机
```

战前估算 `estimateWinRate` 不是另一套规则，而是复用 `calcUnitATK` / `calcUnitDEF`，再按和实战类似的随机区间做蒙特卡洛估算。这一点很重要：玩家看到的胜率、AI 判断、自动战斗结果不能各算各的。

围城也不是普通野战换皮。守军可以来自真实部队，也可以来自城市守军构造出的虚拟 unit；城防倍率会读取城市耐久、城墙、豪族防御支持、守将技能等。战后会写回城市归属、守军、民心、豪族、战利品、声望和事件钩子。

这和 Demo 设计相关，因为 Demo 文档中的手动战斗不是全微操，而是主帅通过前进、停止、冲锋、撤退等粗粒度命令影响战局。因此手动战斗可以被看作：

```text
同一套 Battle Core
  + 实时表现
  + 玩家命令带来的临时 modifier
```

本 repo 可参考的是规则层拆法，不是表现层。3D 战场可以后续承接同一套输入输出：部队指标、命令修正、地形、士气、补给、战斗事件流、战报回写。

Repo 入口：

- `src/chains/military.js`
  - `_squadBase` / `squadATK` / `squadDEF` / `calcUnitATK` / `calcUnitDEF`：战斗指标底层。
  - `resolveBattle`：野战自动结算核心。
  - `estimateWinRate`：战前胜率估算，复用战斗公式。
  - `resolveSiegeBattle`：围城/攻城结算。
  - `calcBreakoutChance`：被围部队突围。
  - `doRetreat` / pursuit 相关函数：撤退和追击。
- `src/render/battle_anim.js`
  - 战斗表现和战报展示逻辑，可以只看输入输出关系。
- `src/render/battle_modals.js`
  - 战前选择、战斗确认等 UI 入口。
- `src/chains/gentry.js`
  - `_applySiegeAftermath` / `_onSiegeAftermath`：攻城后处置对豪族、民心、人口、声望的影响。

## 8. 战役事件、主线压力和持续时间推进

本 repo 用统一 tick 推进持续时间制。每一旬按固定顺序推进经济、人口、建设、军事、政治、事件、AI 等系统；事件系统把主线、危机、承诺、民变、封赏、朝议等内容挂到模拟结果上。

底层逻辑可以拆成五步：

```text
输入
  - 当前时间 G.turn / 年月旬
  - 城市状态：粮食、人口、民心、豪族、围城、占领
  - 部队状态：位置、兵力、士气、补给、任务
  - 武将状态：忠诚、官职、关系、承诺、俘虏、死亡
  - 势力状态：资源、外交、阶段、朝议、科技
  - 事件定义：trigger / condition / choices / effects

状态
  - G._eventCooldown：事件冷却
  - G._eventCatCooldown：事件类别冷却
  - G._eventFired：一次性事件记录
  - G._eventQueue：本旬事件队列
  - G._eventPromises：承诺、期限、惩罚

结算
  - tick 先推进底层模拟：经济、人口、豪族、后勤、部队、政治
  - 事件系统读取模拟结果，检查 trigger 和 condition
  - 满足条件的事件进入队列
  - 玩家或 AI 做选择后执行 effects
  - effects 写回资源、忠诚、地方、外交、部队、事件标记等状态
  - 承诺类事件在后续 tick 检查履约或逾期惩罚

输出
  - 主线推进
  - 危机提示
  - 政策选择
  - 武将封赏/索求/背离
  - 民变、叛乱、地方暴动
  - 战后后果和声望变化

跨系统影响
  - 事件不替代模拟，而是读取模拟压力并把它转成玩家决策
  - 缺粮、低民心、低豪族忠诚、战败、俘虏等都可以成为事件条件
  - 事件 effect 再反过来改变经济、武将、地方、军事和外交
```

这和 Demo 设计相关，因为 Demo 是持续时间制，不是回合制；玩家可以暂停、调速，下达治理、建设、任命、调粮、编制、作战命令。持续时间制最容易出问题的是系统各算各的，最后没有清晰节奏。这里的参考价值在于：所有模块都被 tick 统一调度，事件系统再把模拟结果转化为玩家能感知和处理的主线压力。

Repo 入口：

- `src/core/tick.js`
  - 持续结算周期的主入口，建议先看调用顺序。
- `src/data/events.js`
  - 事件定义。
- `src/chains/event.js`
  - 事件触发、条件、选择、效果、冷却、队列。
- `src/core/hubs.js`
  - 事件承诺、履约、逾期惩罚等跨系统 hub。
- `src/chains/politics.js`
  - 朝议事件和政策提案。
- `src/chains/general.js`
  - 武将死亡、归降、继承、封赏等事件后果。

## 9. 建议用 AI 阅读 repo

这个 repo 不适合靠人工从头读到尾。更合理的方式是把 AI 当成代码导览工具，让它按机制板块读文件、提炼状态、调用链和关键公式。

建议流程：

```text
第一轮：让 AI 只读入口和数据

  - src/core/main.js
  - src/core/state.js
  - src/data/constants.js
  - src/data/state_county.js
  - src/data/general_base.js

  - 经济：src/chains/economy.js

  - 和 Demo 设计文档里的哪个模块对应
```

## 10. AI 总结时应优先抓的机制结论

用 AI 读 repo 时，不要让它只做“文件摘要”。更有价值的是让它提炼可迁移的机制结论。

建议让 AI 优先回答这些问题：

- 经济循环里，哪些变量是输入，哪些变量是状态，哪些变量只是 UI 展示？
- 粮食压力是如何从库存和净产，传导到民心、人口、驻军、调粮和事件的？
- 人口质量如何影响产出，又如何被徭役、战乱、设施恢复？
- 属县 loyalty 如何聚合成 city.gentry，又如何反过来影响税收、征兵、城防和腐败？
- 太守为什么不只是一个加成槽，而是连接武将身份、地方接受度和治理效率的接口？
- 武将标签如何进入派系、朝议、忠诚、地方家族和战斗表现？
- 部队 ATK/DEF 是如何从兵力、士气、兵种、将领、适性、地形、补给合成的？
- 战前胜率和实际战斗是否复用同一套指标？
- 补给覆盖图如何从城市、地形、敌军、领地、地方支持生成？
- 事件系统是如何读取模拟状态，并把它转成主线压力和玩家选择的？

最终输出建议让 AI 固定成这种格式：

```text
机制名称：

一句话定义：

核心状态：

核心结算：

关键函数：

相关 Demo 模块：

可参考点：

不要照搬的点：
```

本 repo 的核心参考价值，是这些系统已经在一个可运行原型里互相咬合过。数值、UI、JS 全局写法都不重要；真正应该抽取的是各板块之间的接口、状态边界和因果关系。
